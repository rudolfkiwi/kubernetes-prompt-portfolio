# Kubernetes Manifest Prompt Portfolio

A portfolio of **original English prompts for Kubernetes manifest generation and analysis**, based on nine examples in the [go-demo-app YAML directory](https://github.com/den-vasyliev/go-demo-app/tree/master/yaml).

## Prompt portfolio

Each entry provides a ready-to-copy **PROMPT**, a short **DESCRIPTION**, and a relative **EXAMPLE** link to a generated or adapted YAML manifest in this repository's root `yaml/` directory. Generation and analysis prompts are separate rows, so every reference manifest has both.

## Usage

1. Choose a **Generation** prompt from the table and ask an AI assistant to produce the YAML. The corresponding file under `yaml/` is a prepared example of the expected result.
2. Choose the corresponding **Analysis** prompt and paste the full contents of its YAML file after the prompt. Review the findings, separating manifest facts from assumptions about a running Kubernetes cluster.
3. Check syntax locally and, when a suitable Kubernetes cluster is available, use server-side dry-run validation:

```bash
python3 -c "import pathlib, yaml; [yaml.safe_load(p.read_text()) for p in pathlib.Path('yaml').glob('*.yaml')]"
kubectl apply --dry-run=client -f yaml/app.yaml
kubectl apply --dry-run=server -f yaml/app.yaml
```

> **Compatibility and safety:** The examples are educational and not guaranteed production-ready. The `app-livenessProbe.yaml` probe port intentionally differs from the declared container port and requires runtime checking. `app-volumeMounts.yaml` uses node-local `hostPath`. `app-job.yaml` mirrors a historical GCE volume source and uses `gsutil rsync -d`, which can delete files at the destination; do not run it without review. `app-secret-env.yaml` requires an existing Secret named `mysecret1` in the same namespace. `app-cronjob.yaml` has been updated to `batch/v1` for current Kubernetes API compatibility. Client-side parsing alone cannot validate cluster-specific capabilities or the availability of images, disks, or cloud credentials.
